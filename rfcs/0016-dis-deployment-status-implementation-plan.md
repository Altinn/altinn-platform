# Implementation plan: DIS deployment status

Extend `dis-console` with a durable deployment-status API so product workflows can wait for a specific release to reconcile and complete its application rollout. Pilot with Dialogporten in `at23`, reuse the existing cluster agents and central read model, and provide a shared GitHub Action for other DIS products. This is the delivery checklist for [RFC 0016](0016-dis-deployment-status.md). Implementation and deployment follow acceptance and separate changes.

## Scope

- In: attempt registration, exact artifact correlation, application rollout checks, durable outcomes, repository/product/environment authorization, a shared wait action, and Dialogporten `at23` integration. Success means the requested application manifest revision reconciled and its required application workloads completed their rollout.
- In: propose an authenticated central HTTPS endpoint using GitHub Actions OIDC, subject to confirming existing DIS gateway conventions. Cluster collection remains read-only.
- Out: migration execution, migration completion gates, smoke tests, automatic rollback, deployment commands through the API, a new console UI, and onboarding every product/environment in the first release. Existing migration and smoke-test workflows remain independent.
- Prerequisite: [Dialogporten manifest PR #86](https://github.com/Altinn/dialogporten-manifests/pull/86) publishes both OCI bundles to all environment tags (`at23`, `tt02`, `yt01`, `prod`) on every commit to `main`. Integrate with that publisher and verify its Flux source/path wiring. Add independent per-environment promotion in a later change before enforcing this plan's attempt ownership; the initial all-tag publication does not isolate releases by environment. Immutable digests identify individual releases.
- Evidence: research checked upstream `altinn-platform` at `b5e1ed6d`, `dialogporten` at `b2f31ccf`, `dialogporten-manifests` at `813149a5`, core at `d2ce5296`, DIS modules at `a99c8110`, and shared manifests at `4a2da410`. These are source observations, not verified deployed state. Refresh the baseline before implementation.

## Action items

- [ ] **1. Verify the implementation baseline and pilot wiring.** Refresh each affected repository and prepare isolated task branches/checkouts, preserving unrelated work. Read current scoped instructions and confirm SDK/CI pins. Verify the deployed console/agent versions, agent coverage for `dis-core-at23-aks`, served Flux API versions, current publisher action pin, endpoint ownership, and runner connectivity. Follow repository approval requirements for live commands. Use the observed application resource `product-dialogporten/dialogporten-apps` and source `dialogporten-manifests` as pilot candidates; configure resource mapping explicitly rather than deriving bootstrap names. Deliver a confirmed dependency and configuration inventory before rollout work.

- [ ] **2. Define the versioned API and deployment lifecycle.** Add an API contract alongside `services/dis-console`: `POST /api/v1/products/{product}/environments/{environment}/deployments`, `PUT /api/v1/deployments/{id}/artifact`, and `GET /api/v1/deployments/{id}`. Add `POST /api/v1/deployments/{id}/events` for authorized publication-failure, cancellation, and supersession events; callers cannot assert deployment success. Registration records repository identity, full application SHA, workflow run/attempt, target mapping, required workloads, deadline, and an idempotency key. The publisher attaches full manifest SHA, OCI repository, immutable upstream manifest digest, and expected workload image references. Pin runtime images by digest or establish an enforceable immutable-tag policy for the pilot. Make receipt attachment immutable and idempotent; reject conflicting retries. Return structured checks, failure stage/reason, timestamps, freshness, and retry guidance. Specify states `pending`, `progressing`, `succeeded`, `failed`, `timed_out`, `superseded`, `cancelled`, and `unknown`; only the outcome states are terminal. An HTTP 200 means a status was retrieved, not that deployment succeeded.

- [ ] **3. Add durable attempt storage and concurrency control.** Extend the central schema/store with attempts, immutable artifact receipts, evidence, state transitions, and deadlines. Store this separately from resource snapshot/history retention so finalized results survive subsequent rollouts and agent restarts. Use transactional uniqueness for idempotency and one active promotion per product/environment; return a retryable conflict for another attempt instead of relying on GitHub concurrency as a FIFO queue. Require an explicit authorized supersession decision and preserve the replaced attempt's outcome. Specify publisher fencing/serialization before releasing an environment to another attempt; a console transaction cannot prevent a late registry write from an old runner. Cancellation stops tracking and does not undo an already-promoted artifact. Run evaluation/deadline processing independently of polling clients. Use additive migrations and document mixed-version agent/server compatibility and retention defaults.

- [ ] **4. Collect and evaluate evidence for the requested release.** Extend `internal/flux`, tenant storage, and central synchronization with separate applied/attempted revisions, relevant conditions and their observed generations, suspension, workload rollout counters, expected images, and successful sweep/sync timestamps. Evaluate only configured sources, Kustomizations, and required workloads, using coherent collection evidence. Require current generations, matching upstream artifact identity, successful application reconciliation, and completed workload rollout for success. Deployment `Available=True` alone is insufficient. Source artifact revision identifies the upstream OCI digest; do not substitute Flux's stored-artifact checksum. Transient errors remain progressing with diagnostics; attributable terminal errors fail; unavailable/stale evidence becomes unknown until recovery or the attempt deadline. Default to 30-minute attempt deadlines and a two-minute freshness threshold, both configurable. Preserve terminal evidence separately from current health. Pilot one cluster per attempt with explicit Deployment policies. V1 must reject unsupported rollout kinds/policies rather than accept them as healthy.

- [ ] **5. Secure and expose the central API.** Select the existing gateway pattern if available; otherwise implement GitHub OIDC validation with signature/JWKS verification, issuer, audience, lifetime, immutable repository/owner identity, and permitted workflow/ref/environment claims. Map callers to products/environments server-side. Distinguish the application workflow's registration/read permissions from the manifest publisher's receipt/reporting permissions. Restrict responses to approved status fields and redact sensitive diagnostics. Expose only the intended API routes through TLS, add request limits and audit records, and verify unprotected legacy/raw-resource routes are not reachable through this endpoint. Place deployment manifests in `altinn-platform`; use the owning infrastructure checkout for routing/identity changes only after ownership is established.

- [ ] **6. Carry a deployment receipt through publication and environment promotion.** Extend `actions/flux/build-push-image` and the Dialogporten manifest workflows to carry the attempt ID, check out an explicit manifest commit, publish an immutable artifact, and return its exact digest. Attach the receipt successfully before promoting the environment tag; make retries safe if receipt attachment or promotion fails. Separate upload from promotion where the existing action combines them. Integrate with Dialogporten's planned environment-tag publishing rewrite instead of introducing a second tag migration. Verify each OCI source selects the intended environment tag and artifact path. Record the tag and the exact digest from the publishing operation; never reconstruct an attempt by resolving the mutable tag later. Keep syncroot and application artifact identities distinct even when their tag names match. As a follow-up to the initial all-tag publisher, scope promotion to the requested environment before enforcing the gate, enforce active attempt ownership across every promotion path, and handle already-current images with verified evidence rather than an automatic success. Add publication-failure reporting so a rejected dispatch/build does not silently wait for a cluster timeout.

- [ ] **7. Establish Dialogporten's rollout health contract.** Update `dialogporten-manifests/flux/syncroot` to check the explicit required application Deployments, with deliberate timeout and retry settings. Verify readiness probes and rollout strategies support the chosen completion semantics, including intentional zero-replica workloads. Keep infrastructure provisioning and suspended CronJobs outside the v1 application completion gate. The migration manifest is a suspended CronJob and cannot establish that a migration ran. Render every affected overlay, verify the pilot selects the correct environment path and artifact tag, and confirm the bootstrap/application resource relationship against deployed configuration. Update essential deployment documentation where these publishing contracts change.

- [ ] **8. Integrate the reusable wait action and pilot caller.** Resolve action ownership with [the pending migration to dis-way/actions](https://github.com/Altinn/altinn-platform/pull/3926), then add a shared action that accepts an attempt ID, obtains/refreshes an OIDC token, polls with 15-second jittered intervals, respects retry guidance and a bounded client deadline, and outputs the terminal state plus diagnostic links. Handle transport errors and stale observations separately from deployment failures. Update `dialogporten/.github/workflows/workflow-dispatch-update-manifests.yml` and its callers to register before dispatch, carry the ID into the manifest repository, and wait after dispatch. Exit successfully only on succeeded; report failed, timed-out, superseded, or cancelled attempts distinctly. Ensure existing Azure Container Apps results and DIS results are identified separately while both delivery paths coexist.

- [ ] **9. Validate correctness, isolation, and recovery.** Add meaningful evaluator/API/storage tests for previous-release green status, revision changes without generation changes, new pods failing while old pods remain available, source/build/apply failures, transient retries, stale or partially collected evidence, missing resources, paused reconciliation, zero replicas, duplicate/conflicting receipts, cross-product access, overlapping attempts, supersession, cancellation, and process restarts. Verify missed historical transitions never manufacture success and a healthy previous version never satisfies a newer target. Test publication-before-promotion ordering, pipeline no-op/retry paths, two successive digests under the same environment tag, and independent promotions in different environments. Run `make setup-local-env` and `make run-checks-ci-cache` for console code changes, plus `make test-e2e-kind-ci` for database/schema changes using a disposable local cluster under applicable permissions. Run action/workflow validation and offline Kustomize rendering. Record checks actually run and environmental limits.

- [ ] **10. Roll out additively and establish exit criteria.** Release backward-compatible storage/agent changes first, then the server/authentication layer, then pinned publishing/wait actions and pilot manifest/workflow changes once Dialogporten's environment-tag publishing rewrite and the follow-up for independent promotion are available. Deploy through normal review and release processes when authorized. Run the pilot gate in observation mode before making it required; verify successful rollout, deliberately broken image, stalled source, unavailable agent, and competing releases in an approved test environment. Enable enforcement only after outcomes consistently match direct rollout evidence and repository isolation is demonstrated. Monitor evaluation lag, stale clusters, active-attempt age, terminal outcomes, and authentication failures. Roll back enforcement independently of application delivery; retain attempt history and use additive schema compatibility. Finish with a short product-onboarding contract and the list of upstream versions required by each consumer.

## Open questions

Resolve the complete decision list in [RFC 0016](0016-dis-deployment-status.md#unresolved-questions), including publisher fencing, image identity, retention, and action ownership.

- **Endpoint placement:** Which DIS gateway and infrastructure checkout should own central API exposure? Default proposal: authenticated HTTPS with GitHub OIDC, using current gateway conventions if available.
- **Pilot health mapping:** Which `at23` Deployments must complete, and is any intended to scale to zero? Confirm this during baseline verification; migrations and smoke tests are excluded from v1 success.
- **Observation coverage:** Are the required console agents and compatible Flux versions deployed in the pilot path? Verify before enabling the gate; do not infer availability from source manifests.

Coordinate with [RFC 0010 / PR #3220](https://github.com/Altinn/altinn-platform/pull/3220) and [flux-dispatch implementation PR #3925](https://github.com/Altinn/altinn-platform/pull/3925) on release identity and outcome vocabulary. This plan does not depend on those proposals; any event integration is optional.
